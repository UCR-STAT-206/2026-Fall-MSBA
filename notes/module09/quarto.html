Publishing a Quarto Website

Goals

  1. Describe the parts of a Quarto website project and how they fit together.
  2. Build a website locally with a dedicated Micromamba environment.
  3. Publish the website to GitHub Pages with quarto publish.
  4. (Optional) Publish automatically with a GitHub Action.

Overview

  • A Quarto website is a folder of .qmd files plus a configuration file, _quarto.yml, that ties them together with shared navigation and styling.
  • Quarto renders each page to HTML. The rendered site is a folder of plain files that any web server can host.
  • GitHub Pages is a free hosting service that serves a website from a branch of a GitHub repository.
  • The repository holds two things: the source (.qmd files, data, configuration) on main, and the rendered site on a separate branch named gh-pages. Naturally, you can also include Python source files as part of the project.
  • These notes describe the workflow at a high level. Consult the Quarto documentation for the details of each step, and expect to look things up as you go.

Our running example is a small website about the Palmer penguins with four pages: a home page, an introduction to the data, an exploratory data analysis, and a regression analysis.

1. Create the repository

Create the repository on GitHub first, then clone it (see Git). This sets up the remote and the default branch automatically.

  • If creating on GitHub’s interface, be sure to check “Add README.md” so that the repo starts with an initial commit.
  • Keep the repository public. GitHub’s free plan offers Pages only for public repositories.

2. Create the environment

Write an environment.yml for the project and create the environment (see Conda/Micromamba):

name: quarto_web
channels:
  - conda-forge
dependencies:
  - python=3.14
  - ipykernel
  - jupyter
  - matplotlib
  - pandas
  - seaborn
  - statsmodels
micromamba create --name quarto_web --file environment.yml
  • Quarto uses jupyter to run Python code chunks, so it must be in the environment.
  • Be sure to commit environment.yml with the rest of the project.

3. Set up _quarto.yml

_quarto.yml sets the project type (website), the navigation bar or sidebar, the theme, and options shared by every page. Quarto can generate a starter project:

quarto create project website .

This creates a _quarto.yml, an index.qmd, and a stylesheet in the current folder. Edit _quarto.yml to match the pages you plan to write. See the website documentation for the available options.

4. Add the pages and data

  • Create one .qmd file for every page listed in _quarto.yml, even if it starts empty. In our example: index.qmd, intro.qmd, eda.qmd, and regression.qmd.
  • Commit the data files the pages read, such as penguins.csv.
  • Add the folders Quarto generates, _site/ and .quarto/, to .gitignore. These are build outputs and should not be tracked in the repo’s history.

5. Build the site

Activate the environment and start a preview:

micromamba activate quarto_web
quarto preview
  • quarto preview renders the site and opens it in a browser.
  • It re-renders a page each time you save it.
  • The Quarto extension for VS Code provides the same command.

Commit small changes as you build the site.

6. Push to GitHub

  • Push the source to main.
  • If you develop on branches, merge them into main through pull requests.
  • The rendered site is never committed to main.

7. Publish

From the main branch, with the environment active, run:

quarto publish gh-pages

This command

  1. asks you to confirm,
  2. renders the site on your machine,
  3. copies the output to a branch named gh-pages, creating the branch on the first run,
  4. pushes that branch to GitHub, and
  5. opens the published site in your browser.

For a project repository, no settings need to change on GitHub. To update the site, repeat steps 5 through 7.

WarningOutdated instructions

Older tutorials, and possibly LLM answers, tell you to create the gh-pages branch by hand and to configure Pages before publishing. Current versions of Quarto do this for you. Check advice against the Quarto documentation.

8. (Optional) Publish with a GitHub Action

A GitHub Action is a script that GitHub runs on its own servers when something happens in a repository. Quarto provides an Action that renders the site and pushes it to gh-pages whenever main changes. Once you set this up, you no longer have to run quarto publish yourself.

  • The Action needs the gh-pages branch to exist, so run quarto publish gh-pages locally at least once first.
  • The workflow is a short file saved as .github/workflows/publish.yml. Copy it from the Quarto documentation rather than from an LLM, which may give outdated versions.
  • Each run appears in the repository’s Actions tab with a green check or a red X. When a run fails, the log shows which step failed. Read it the way you read a traceback.

Who runs the Python code?

GitHub’s servers start with nothing installed. There are two options.

Freeze the computations

Add the following to _quarto.yml:

execute:
  freeze: auto
  • Running Quarto locally saves the results of each page’s code in a _freeze folder.
  • Commit this folder if you do not want to handle additional setup in the GitHub Action file.
  • The Action reuses the saved results and does not run any Python.

The workflow becomes:

  1. Edit locally with the project’s Conda/Micromamba environment active.
  2. Run quarto render.
  3. Commit the updated _freeze folder.
  4. Push to main.

If you push a changed .qmd file without rendering it first, the Action tries to run that page’s code and fails, because Python is not installed on GitHub’s servers.

Rebuild on GitHub

Alternatively, the workflow you specify can install Python and every package before rendering.

  • Quarto’s documented example uses pip and a requirements.txt file.
  • Reusing environment.yml requires an extra step that sets up Micromamba, such as the mamba-org/setup-micromamba Action.
  • This approach is slower, since every push reinstalls the packages, but adds a layer of reproducibility to your work.
